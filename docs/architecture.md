# FlexAnnotate — Architecture

FlexAnnotate is a bootstrapped Zotero plugin written in TypeScript and built with zotero-plugin-scaffold (version 2.0.0, `strict_min_version` 7.0, `strict_max_version` 10.\*). It is developed against Zotero 10.0.5 and run through the automated suite on 7.0.32, 8.0.4, 9.0.6 and 10.0.5/10.0.6 (`npm run test:versions`); see the README for what each version supports. It offers print annotations, citation-only insertion, Citavi import and an organizer (a fork of Lattice). Version 1.2.0, written in vanilla JS, is at the tag `pre-merge`.

References like `xpcom/integration.js:1678` are paths inside `chrome/content/zotero/` of Zotero's `omni.ja`. Unless marked "(10.0.1, not rechecked)" or given with another version, they were checked against 10.0.5. All anchors by version: [anchors.md](anchors.md).

## Layers

```
src/core/            pure logic shared by several features (locator, print dialog view, page-label popup)
src/shared/          feature registry, checked patching, citation dialog watcher
src/features/<f>/    one folder per feature; talks to Zotero; <f>/logic/ holds its pure logic (no Zotero imports, tested with node --test)
src/prefs/           script of the preference pane (separate bundle)
src/utils/           locale, prefs, menu registration, ztoolkit
```

Dependencies point downwards: features import `core`, `shared` and `utils`; `logic/` and `core` import nothing from Zotero and never from another feature. Features: `print`, `citeOnly`, `citavi`, `reader`, `organizer`. `src/hooks.ts` is the only place that knows all features.

## Feature lifecycle

`src/shared/feature.ts` defines `Feature` with optional hooks `start`, `stop`, `addToWindow`, `removeFromWindow`. `startAll`, `stopAll`, `addToWindow` and `removeFromWindow` call them in order (stop in reverse) and log a failing hook without aborting the others or throwing.

`hooks.ts` holds the ordered `features` array and runs it:

1. `onStartup` waits for Zotero, calls `initLocale()`, exposes `addon.api` (used by the Zotero tests), registers the preference pane, runs `startAll(features)`, then `onMainWindowLoad` for every open window.
2. `onMainWindowLoad` inserts the FTL files and runs `addToWindow(features, win)`.
3. `onMainWindowUnload` runs `removeFromWindow`; `onShutdown` runs `stopAll`.

Global work (patches, observers, `MenuManager` menus) belongs in `start`/`stop`; DOM belongs in `addToWindow`/`removeFromWindow`. Both must be idempotent and check for their own element IDs.

## Feature registry and disablable modules

`src/hooks.ts` no longer lists the features itself. The switches live in `src/features/gates.ts` (pure `gates` array with an `enabled` flag and optional `requires` dependencies per feature). Every feature and sub-feature is listed as a `FeatureGate`:

1. **Lifecycle features & dialog injectors:** Derived by `src/features/registry.ts` through `activeGlobalFeatures()` and `activeDialogInjectors()`, each filtered by `isFeatureEnabled(name)`. `hooks.ts` calls them once in `onStartup` (not at import, so the pref overrides below are already readable).
2. **Runtime sub-features:** Checked at call and render sites via `isFeatureEnabled(name)` (e.g. `citedTracking`, `footnoteJump`, `narrowDialogLayout`, `dialogShowPlace`, `outlineAnchorTags`, `outlineScopeHeading`, `docImport`, `docExport`, `noteExport`, `orphanTags`, `readerLabelPopup`, `citaviPrintQuotes`, `citaviLinks`, `citeprocResetFix`).

Coupled features declare their base feature via `requires`. Disabling a base feature (e.g. `organizer` or `citeOnlyPatch` or `citationDialog`) cascades cleanly and automatically disables all dependent entry points, sub-features, and associated preference controls in `preferences.ts`.

**Hotfix switch without a release:** every gate can be switched off at runtime with the hidden boolean pref `extensions.flexannotate.gate.<name>` (about:config → create a boolean, set `false`). Only an explicit `false` counts, so an override can switch a feature off but never on, and a source-level `enabled: false` always wins. Runtime sub-feature gates take effect on the next render/action; lifecycle features and dialog injectors are evaluated at startup and need a Zotero restart. Dependents follow through `requires`. The default reader sits in `gates.ts` (`setGateOverrideReader` replaces it in tests); it resolves `Zotero` at call time and fails open on any error. The pref keys are not registered in `prefs.js`, so they do not show up in the generated typings and are not part of the settings UI.

A consistency unit test (`test-unit/featureGates.test.ts`) enforces that every registered feature, injector and runtime sub-feature has a gate, all `requires` targets exist, and disabling a base feature cascades cleanly to dependent entry points. `test-unit/gateOverrides.test.ts` covers the pref override, and the Zotero smoke test `test/gates.test.ts` switches every gate off in turn, runs the stop/start/addToWindow/removeFromWindow cycle and opens the organizer, failing on any logged feature error. The smoke test covers the lifecycle and the organizer window only; render paths in the citation dialog are not exercised with a gate off.

Self-contained feature logic lives in dedicated files so it can be replaced or adapted to new Zotero APIs without touching the surrounding dialog:

- **Persistent citation window** (`dialogPersistent.ts` is a compatibility barrel): `persistentState.ts` (shared state, prefs, logging), `persistentPinning.ts` (keep/save window geometry), `persistentWindow.ts` (open/close/insert, `displayDialog` patch), `persistentPatches.ts` (execCommand/interface/progress patches), `persistentFeature.ts` (start/stop), `persistentTestHooks.ts`; pure logic in `logic/persistentOptions.ts`, `logic/persistentRect.ts`, `logic/lastCommand.ts`.
- **Cited tracking and footnote jump** (`dialogCited.ts` is a compatibility barrel): `citedTracking.ts` (green check, footnote mapping, session reconcile), `citationJump.ts` (Word/LibreOffice jump incl. VBS), `citationShared.ts` (session access and jump lock); pure logic in `logic/cited.ts`.
- **Outline view**: `dialogOutline.ts` (injector/regie), `dialogOutlineRender.ts` (tree/list/preview/insert), `dialogOutlineLayout.ts` (three-column and narrow <750 px layout), `citedToggle.ts` (green check), `footnoteChips.ts` (footnote badges/popover + jump).

## Data model

All data lives in Zotero's own structures (tags, notes, child items), so it syncs and survives a plugin removal.

| Datum                                  | Where                                           | Meaning                                                                                                                                                                                                         |
| -------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `#flexannotate-placeholder`            | tag on the placeholder attachment               | marks the generated PDF that carries print annotations                                                                                                                                                          |
| `#flexannotate-locator-<type>`         | automatic tag on an annotation                  | CSL locator type; absent for `page` unless the document default differs                                                                                                                                         |
| `#flexannotate-default-locator-<type>` | automatic tag on an attachment                  | default locator for annotations created later; `page` is never tagged                                                                                                                                           |
| `§Title`                               | tag on annotations, works and the outline note  | files the item under the outline heading `Title`; the `★outline` note anchors every heading's `§`-tag so it exists even without a filed item                                                                    |
| `★outline`                             | tag on a standalone note                        | the note holds the outline tree as JSON after the sentinel `LATTICE-OUTLINE-V1`                                                                                                                                 |
| `flexannotate_cited`                   | Word/Writer doc variable (`session.data.prefs`) | JSON string mapping `citationID -> annKey[]` and `manual: annKey[]`; travels with `.docx`/`.odt`, survives restarts, reconciled with `session.documentCitationIDs` (see [cited-tracking.md](cited-tracking.md)) |
| `citedAnnotations`                     | preference (fallback)                           | legacy per-document session id storage: annotation id to work id, at most 50 documents                                                                                                                          |

### Placeholder attachment

Zotero accepts annotations only under a file attachment with an `attachmentReaderType` (`xpcom/data/item.js:2246-2259`; reader types from the content type, `:3530-3540`). A regular item or a linked URL as parent throws on save. `placeholder.create()` therefore imports a generated one-page PDF (`src/features/print/logic/printAnnotation.ts: buildPlaceholderPDF`) as a child, titled from `placeholder-title`, and tags it. The file is generated at runtime because `Zotero.Attachments.importFromFile()` needs a real path and `rootURI` inside an XPI is a `jar:` URI. `isPlaceholder()` checks the tag, not the title. `cleanUpIfEmpty()` erases the placeholder after its last annotation unless `keepEmptyPlaceholders` is set.

### Annotation field rules

Enforced by Zotero in `xpcom/data/item.js` (10.0.5 line numbers):

| Rule                                                                             | Line         |
| -------------------------------------------------------------------------------- | ------------ |
| `annotationType` must be set before any other annotation field                   | `:4511`      |
| Type changes only between `highlight` and `underline`                            | `:4518-4520` |
| `annotationText` only for `highlight` and `underline`                            | `:4530-4531` |
| `annotationColor` must match `/#[a-f0-9]{6}/` (lowercase)                        | `:4537`      |
| `annotationSortIndex` must match `/^\d{5}\|\d{6}\|\d{5}$/` for a PDF parent      | `:4547`      |
| `annotationPageLabel` is saved as `pageLabel \|\| null` and reads back as `null` | `:2290`      |

`printAnnotations.create()` sets the type first, folds quoted text into the comment for type `note`, falls back to `#ffd400` for invalid colors and writes a fixed `annotationPosition` (`pageIndex` 0, one zero rect), because the PDF parent requires the field and no geometry exists. The printed page goes into `annotationPageLabel`; `buildSortIndex()` takes the first digit run, clamps it to 99999 and pads it, so a label without digits sorts last.

### Locator type

`core/locator.ts` resolves the locator in this order: tag on the annotation, default tag on the attachment, `page`. `setDefaultLocator()` first freezes existing annotations without an explicit tag to the previous default, so changing the default never alters old annotations. `applyLocatorTag()` removes old locator tags before writing the new one.

### Outline note

`src/features/organizer/logic/outline.ts` and `organizer/outlineModel.ts` read and write the note. Zotero rewrites `<pre><code>` to `<pre>` on save; the reader accepts both. Numbers such as `1.2.3` are computed for display and never stored. Format and tags are compatible with Lattice.

`OutlineModel.save()` creates the note with `saveTx({ skipSelect: true })` and renders its `<h1>` heading from the scope: the library name for the library-wide tree (`Zotero.Libraries.get(libraryID).name`), or the name of the main collection (`Zotero.Collections.getByLibraryAndKey(libraryID, collectionKey).name`) — `scopeName()`. Because Zotero derives a note's list title from the first line of its content (`getNoteTitle` → `noteToTitle`, `xpcom/data/item.js`), this makes several outline notes distinguishable in the item list. `serializeOutline(roots, scopeName)` only changes the `<h1>`, never the JSON; `outlineHeading`/`outlineHeadingOf` (pure, `logic/outline.ts`) build and read it. `load()` calls `syncNoteHeading()`, which rewrites only the first `<h1>` if it differs, so an older note gets its scope name backfilled on first open. `save()` applies the heading `§`-tags inline via `applyAnchorTags()` on the saved note (new or existing), so every heading's tag exists in the library and Zotero's PDF-reader tag autocomplete suggests it even when no item is filed yet; stale `§`-tags (renamed/deleted headings) are dropped. `load()` then calls `syncAnchorTags()`, which uses `applyAnchorTags()` + `saveTx()` to backfill older notes on first open; both syncs are idempotent and skip the write when nothing changed. The note itself never counts as a filed item: `gather` and `buildCountMap` skip notes carrying `★outline` (`isOutlineNote`). If several notes carry `★outline` (for example after a sync conflict), `findNote()` takes `pickNewest()` (`src/features/organizer/logic/outline.ts`): latest `dateModified`, on a tie the higher id, so the result does not depend on the input order. See pitfall 14.

## Control flow

### Create a print annotation

1. `printMenus` (`menus.ts`) adds a separator and three entries to `zotero-itemmenu` and toggles them on `popupshowing` through `src/features/print/logic/printMenuState.ts`.
2. The entry calls `dialog.open(win, item)`, which awaits `Zotero.Styles.init()`, builds a XUL `<panel>` once (`parseXULToFragment`) and fills locator and color menulists.
3. On save, `printAnnotations.create()` calls `placeholder.ensure(item)`, creates the annotation under it and applies the locator tag.
4. Edit and delete use the same panel; `annotationRowMenu.ts` adds a popup for `annotation-row` elements in the item pane via one capture-phase `contextmenu` listener on the document.

### Citation-only insertion

1. `citeOnlyPatch.start()` replaces `Zotero.Integration.Session.prototype._insertCitingResult` (`xpcom/integration.js:1678`) through `assignChecked`; a failed patch throws and is logged by the registry.
2. Zotero branches there: annotations become a mock note; everything else goes to `_insertItemsIntoDocument()` (`:1778`).
3. With `citationOnly` set, the patched method calls `src/features/citeOnly/logic/citeOnly.ts: citationOnlyItems`. Only when every cited item is an annotation with a citable top-level item does it build a new item list (parent item, `annotationPageLabel` as locator, locator tag as label), assign it to the same citation object and call `_insertItemsIntoDocument()` itself.
4. Any other case, or any error, falls through to the original method. The citation object is mutated, not cloned, because the session later calls `.serialize()` on it (`:1778-1785`).
5. The mode selector is injected into the citation dialog (see next flow) and writes the same preference.

### Citation dialog: shared watcher and injectors

1. `shared/citationDialog.ts` registers one `Services.wm` listener. For each window with `location.href` equal to `chrome://zotero/content/integration/citationDialog.xhtml` it waits until `DIALOG_STATE.loaded` (`integration/citationDialog.js:149`).
2. It then calls every registered `DialogInjector.inject(win)` once, in registration order: first `modeSelector`, then `outlineView` (`organizer/citationDialog/dialogOutline.ts`).
3. `modeSelector` adds the "Einfügen als" select to the settings popup and the item popup and follows `dialog-type` changes with a `MutationObserver`.
4. `outlineView` adds the "Nach Gliederung anordnen" checkbox to the annotations view. When on, it renders tree, list and preview in the dialog's three columns. Inserting clicks the "+" of a hidden native `annotation-row`, so Zotero's own insertion code runs.
   At 750 px and wider the plugin sets no width of its own on `#sidebar`, so the right column keeps Zotero's width with and without the view. Below 750 px `LAYOUT_CSS` stacks the columns, but only in the persistent window (see "Persistent citation window"). The CSS it adds only keeps long rows from widening the layout (`LAYOUT_CSS` in `dialogOutlineLayout.ts`).
   Zotero's own search bar is mirrored into the outline filter: `bubble-input` fires `handle-input` (`detail.query`) on the document (`integration/citationDialog.js:1261`, `elements/bubbleInput.js:333`), and `addSearchSync` writes the query into the plugin's filter field and re-renders. The filter field is never written back.
   With exactly one annotation selected, the preview offers "Zitatstelle anzeigen": `openTarget.openRow()` calls `Zotero.Reader.open(attachmentID, { annotationID: key })` and activates the main window with `Zotero.Utilities.Internal.activate`. The dialog stays open.
5. On `accept`, `hookAccept` (`citedTracking.ts`, exported through `dialogCited.ts`) wraps `io.accept` to record cited annotation ids per document session id. An entry counts as cited while its work is still cited in the document.
6. An unload of the window or `stop()` calls `detach` of every injector. A failing injector does not stop the others.

### Persistent citation window

Opt-in (`persistentCitationDialog`, default off). `dialogPersistent.ts` (logic in `persistentPatches.ts`/`persistentWindow.ts`) patches `Zotero.Integration.displayDialog`, `Progress.prototype.show`, and `Zotero.Integration.Interface.prototype.addEditCitation` / `addAnnotation` (`persistentDialogPatch`, `start`/`stop`). For `citationDialog.xhtml` with the option on, the patch does not call the native function. It opens the window itself (`Services.ww.openWindow`, with `dialog=no`, no `popup`/`alwaysRaised`, and the previous window's position as `left`/`top`), sets `Zotero.Integration.currentWindow` and resolves its own promise on the first of: `io.accept` / `io.cancel`, or `unload` of the window. It keeps `currentWindow` set, so `execCommand` closes the window in its `finally` as usual (integration.js:312-316); the test asserts `currentWindow === w`.

When `addEditCitation` or `addAnnotation` is invoked from a supported word processor (`WinWord`, `LibreOffice`, `MacWord`) with persistent mode enabled, FlexAnnotate intercepts the call to prevent native `Session.prototype.cite` (`integration.js:1536`) from creating an empty placeholder footnote before any citation is chosen (pitfall 25). If the cursor is not in an existing field and there is no `pendingInsert`, the patch validates `canInsertField()`, records `lastCommand`, sets `session._dontActivateDocument = true` (preventing Word from reclaiming focus, `integration.js:326`), schedules `openBrowse()`, and returns `[]` immediately. Only upon user accept in the browse window does `insertFromBrowse()` trigger `execCommand` with `pendingInsert`, which passes through to native insertion.

A new request closes the open window first and opens a new one at the same rect (pitfall 18). Reusing the window is not possible (pitfall 18). After an insert the native dialog is collapsed and its trees are gone (pitfall 19), so the patch never reuses it: the command ends, `openBrowse()` opens a fresh dialog in browse mode at the same rect. A browse window is `citationDialog.xhtml` with a synthetic `CitationEditInterface` (`isAddingAnnotations = true`). Its accept does not run the native accept: `insertFromBrowse()` keeps the chosen items in `pendingInsert` and runs `Zotero.Integration.execCommand(agent, "addAnnotation", docId, templateVersion)` again with the agent and docId of the last command (captured by `patchExecCommand`). In the patched `displayDialog` the pending items are copied into the real io, the browse window closes first (`closeBrowse()` waits for its unload) and the real `io.accept` runs. The browse window reopens when that command ends. A real request closes a browse window; closing it with X ends the persistence until the next request; turning the switch off or `stop()` closes it. The browse window must ignore the `about:blank` unload that precedes its URL load (integration.js:498), or it loses its reference. The patch writes the live inner size to `integration.citationDialog.windowParams` (library and list) after Zotero's own cleanup, and the live rect to the pref `persistentWindowRect` (debounced; read by the first persistent window after a restart, see `readStoredRect`). Zotero stores the outer size before collapsing (pitfall 19); the patch's inner size wins. After opening, `pinRect()` holds the stored position for the load phase only (until 500 ms after `DIALOG_STATE.loaded`, at most 1.5 s), and the size until the first foreign resize after that. It corrects the window from a 20 ms timer and clamps `resizeTo`/`moveTo` to the rect, and it lowers the library layout's minimum width as soon as the page exists. The 200 ms tracking timer only reads the geometry and does nothing after the dialog accepted (`accepted`, a top-level `var` in citationDialog.js:30). Background, evidence labels and limits: [persistent-window-limits.md](persistent-window-limits.md). `relaxDialogMinWidth()` lowers Zotero's minimum widths for this window (pitfall 20). Below 750 px (`matchMedia`, change listener, removed on detach) `dialogOutline.ts` moves the two switches from their row into `#settings-popup` (Zotero's gear menu, `citationDialog.xhtml` 187–196) and hides the row; the same input elements and listeners are moved, so there is one source of truth, and `popupshowing` refreshes their state. `LAYOUT_CSS` (`dialogOutline.ts`) holds the narrow layout below 750 px. It is scoped to windows carrying the attribute `flexannotate-persistent` on the root, which `relaxDialogMinWidth()` sets, so ordinary citation dialogs keep Zotero's layout.

### Citavi import

Zotero's importer walks `//Annotations/Annotation` (nodes with `Quads`) and skips sources without an attachment (`import/citavi.js:76-80`). Quotes on printed sources exist only as `<KnowledgeItem>`.

1. `CitaviImport.patch()` (feature `start`) wraps `Zotero.Translate.Import.prototype.translate`. After a Citavi XML translation it keeps the translation object (`_itemSaver._IDMap`, `_io`).
2. `CitaviImport.addToWindow()` patches `importFile` and `importFromClipboard` of each window's own `Zotero_File_Interface`. The pass runs in their `finally`, after Zotero's own annotation pass (`fileInterface.js:686`).
3. `importPrintQuotes` re-inits the XML stream, collects anchored IDs from `//EntityLinks/EntityLink/SourceID` and creates print annotations for the other `KnowledgeItem`s (colors and text distribution from `QUOTATION_TYPES`, locator type from `PageRange` `<nt>` through the `citaviLocator*` preferences).
4. For quotes it created, it removes the translator's note only if the note starts with `CoreStatement` + `Text` and the remainder looks like a locator (`isPageTail`, at most 60 characters of digits, spaces and hyphens). `citaviKeepNotes` disables this.
   Keywords: `//KnowledgeItemKeywords/OnetoN` holds one text per item, `ID:…;KeywordID:…;…`. The first member is the id of the `KnowledgeItem`, the others are keyword ids (the part after `:` is ignored). `splitOnetoN()` and `resolveKeywords()` (`src/features/citavi/logic/citavi.ts`) match the owner id exactly and look up each keyword name by id. The earlier prefix match (`starts-with`) let id `K1` hit the node of `K10`.
   Duplicates: before saving, `isDuplicateAnnotation()` compares the candidate with the existing annotations of the same work's placeholder: equal page label and equal normalized quote text (markup stripped); with an empty text, the comment counts instead. A second import of the same export therefore creates nothing.
5. `linkContributions` reads `ReferenceReferences/OnetoN` (`Parent;Child1;Child2…`) and adds related-item links between parent and children and among siblings in one transaction. The translator does not do this (`xpcom/translation/translate_item.js:1081-1089` is commented out).

### Organizer window management

1. `OrganizerFactory.open()` enforces a single window per Zotero process. If an organizer window is already open (cached in `OrganizerFactory.currentWindow` or found via `Services.wm.getEnumerator("")`), it un-minimizes (`win.restore?.()`) and focuses (`win.focus()`) that window instead of opening duplicate windows.
2. After closing file pickers or import/export dialogs, `OrganizerFactory.restoreFocus(win)` returns focus to the Organizer window.
3. Toasts in the Organizer view (`organizerDom.ts`) display action buttons on a separate line below the text, make the message clickable, and clamp toast bounds within the visible screen.

### Outline import from Word/LibreOffice

1. The document icon in the outline toolbar (`organizerTree.ts`) calls `docImport.start()`. `pickFile()` uses Zotero's `FilePicker` wrapper (`modules/filePicker.mjs`, which adapts `init()` per version, see anchors.md) with the filter `*.docx; *.odt`.
2. `readHeadings()` opens the file with `nsIZipReader`, rejects entries above `MAX_ENTRY_BYTES` (50 MB) before reading, and reads `word/document.xml` (+ `word/styles.xml`) or `content.xml` through `Zotero.File.getContentsAsync(stream)`. The reader is always closed.
3. `src/features/organizer/logic/docOutline.ts` scans the XML with a small tokenizer (no DOM). DOCX: the level comes from the paragraph's `outlineLvl`, else from its style (`outlineLvl` of the style, style name `Heading n`/`Überschrift n`, `basedOn` chain, last the style id); `w:del`/`w:moveFrom` text is skipped. ODT: `text:h` with `outline-level`; `text:note` and `text:deletion` are skipped. Headers, footers and footnote parts are never read; text boxes are not treated separately.
4. `normalizeHeadings()` makes the levels gapless and, if at least 80 % (and at least 3) of the titles start with a manual number (`STRIP_RE`), reports `numberingDetected`; stripping is applied only if the user ticks the box.
5. `planOutlineImport()` plans an append-merge against the current tree (`reuse` under the same parent by NFC-normalized, case-insensitive title, else `create` as last child; collisions with any existing title become `Title (2)`). When `stripExistingNumbering` is active, existing nodes under the same parent whose titles start with a manual number are matched against the incoming cleaned title. On match, their titles are updated to the clean title and `OutlineModel.renameTag()` migrates associated item tags (`§Title`). `computePlanNumbers()` calculates hierarchical preview numbering (`1`, `1.1` …) taking existing and planned siblings into account. `applyImportPlan()` works on a copy. Only if something is created or renamed, the tree is saved through `OutlineModel.save()`.

## Pitfalls

Rules that still apply. Line numbers are 10.0.5 unless marked.

1. **Silent patch failure.** Assigning to a frozen object does nothing outside strict mode and throws inside it; an Xray expando swallows the write. Always use `assignChecked()` (`shared/patch.ts`): assign in `try`/`catch`, read back, compare identity. CommonJS modules from `require()` run in their own sandbox with frozen `exports` (`resource/require.js`, `resource/loader.sys.mjs`) and are no patch targets.
2. **`Zotero_File_Interface` is not a singleton.** Every window that loads `fileInterface.js` has its own object (`fileInterface.js:179`; the wizard loads it itself, `import/importWizard.xhtml:22`). Patch per window; the failure is silent.
3. **Order of the Citavi passes.** Zotero takes the attachment with `getAttachments()[0]` (`import/citavi.js:76,82`). A placeholder created earlier can receive PDF annotations, so the print pass must run after Zotero's.
4. **Startup cache.** Zotero loads `bootstrap.js` with `ignoreCache: true` (`xpcom/plugins.js:205-210`); the bundled build has no inner script loading of its own. The pane script is the exception, which Zotero loads without it: after changing `preferences.ts`, start once with `-purgecaches` (10.0.1, not rechecked).
5. **XUL parses only in privileged chrome documents.** A plugin cannot register a `chrome.manifest`; `openDialog()` with `file:` or `jar:` URLs gives an empty window. Build UI with `MozXULElement.parseXULToFragment()` in the main window, as Zotero does in `elements/*.js` (10.0.1, not rechecked).
6. **`Zotero.Styles.init()` before locator labels.** `Cite.getLocatorString()` reads `Object.keys(Zotero.Styles.locales)` (`xpcom/cite.js:54`), and `locales` is set at the end of `init()` (`xpcom/style.js:154`). `init()` returns a running initialization as a promise (`:68-77`). `getLocatorString()` creates its per-locale map before filling it (`cite.js:66-67`), so an aborted fill leaves later calls returning `undefined`; fall back to the raw locator name.
7. **Preference pane menulists.** Pane scripts run in a sandbox before the fragment exists (`preferences/preferences.js:313-320`, `translateFragment` at `:355`). Zotero fires a `load` event at each pane child (`:617-618`): listen on `document` in the capture phase and re-check each time. Zotero resyncs late-added menuitems through a `MutationObserver` only if the binding exists (`:516-524`); set `elem.value` after filling instead. The pane needs its own `<linkset>` with the plugin FTL (`preferences_general.xhtml:29`).
8. **Fluent value messages versus XUL labels.** `data-l10n-id` sets `textContent`, a `<menuitem>` shows `label`. Use `Zotero.getString()` for color names (`Zotero.Annotations.COLORS` are `[l10n-id, hex]` pairs, `xpcom/annotations.js:40-42`; the `getString` pattern is from `elements/zoteroSearch.js`, 10.0.1 line 1269, not rechecked).
9. **`strict_max_version` is mandatory on Zotero 10.** Without it the plugin is dropped silently at manifest parsing (tested on 10.0.1 with five otherwise identical plugins). `extensions.strictCompatibility` is `false` in `defaults/preferences/zotero.js:6`, but the toolkit sets `addon.strictCompatibility` itself for release builds (`XPIInstall.sys.mjs:507`, toolkit `omni.ja`, 10.0.1, not rechecked).
10. **Item context menu.** `buildItemContextMenu()` removes only its own `zotero-locate` entries (`zoteroPane.js:4196-4199`) and hides only its known options, so appended plugin entries persist and must manage their own visibility on `popupshowing`. For annotation selections the function returns at `:4680`, before `Zotero.MenuManager.updateMenuPopup` (`:4685`), so `MenuManager` entries never update for annotations. `printMenus` therefore uses DOM, not `MenuManager`.
11. **The plugin scope is global, windows are not.** Module objects exist once per session, elements once per window. State of one interaction belongs on the element (expando on the panel, attribute on the popup), per-window bookkeeping in a `WeakMap`. Do not use a "some window is set up" flag; collect windows and test for empty.
12. **`MenuManager` unregistration needs the returned key.** `registerMenu()` returns a key; `unregisterMenu()` with the raw `menuID` finds nothing (`utils/menu.ts`; `xpcom/pluginAPI/menuManager.js:824,833`). `unregisterAllPluginMenus()` stores the keys.
13. **`Zotero.Reader.open` is wrapped by `readerMenu`** and restored through `assignChecked` on stop (`readerMenu.ts`); `Reader.open` is at `xpcom/reader.js:2917`.
14. **Zotero's note editor can overwrite the outline note.** A note that gets selected in the item tree opens in the note editor, and `EditorInstance._save()` (`xpcom/editorInstance.js:1149`; it calls `item.setNote(html)` at `:1177`) writes the editor's copy back, also for a later change it did not see. Selection after a save is suppressed only for `skipSelect` (`xpcom/data/dataObject.js:1053-1054`; `collectionViewItemTree.js:816, 1040`). `OutlineModel.save()` therefore creates the note with `skipSelect: true`. If the user opens the note in the editor, the editor can still overwrite later organizer saves; nothing in the plugin prevents that. No test opens the note in the editor, so the overwrite itself is derived from the source, not reproduced.
15. **Collection trees are outline notes with a second tag.** Each outline note carries `★outline`; collection trees add `#flexannotate-outline-<collectionKey>` (collection key, not id — the key survives sync). The library tree is the note without an extra tag; `findNote()` filters on it (`outlineModel.ts`). `loadScope()` runs inside `saveChain` (so open renames land in the old tree and two quick switches cannot create two notes), sets `State.scope`, swaps `roots`/`noteID` and resets `node`/`sel`/`renaming` before re-rendering. On window start it also runs for the collection selected in the main window, so scope and tree always match; the first-open confirm appears once per collection.
16. **Heading tags are library-wide; trees are separated by work.** A heading is the tag `§Title` on the item, with no collection part. Renaming, deleting, gathering (export) and counting therefore take a `TagScope` (`outlineModel.ts`): the work ids of the tree's top collection incl. subcollections (`treeWorkIDs`, `organizerData.ts`; `null` = library tree = unrestricted). Two trees with a heading of the same name stay independent as long as their works differ. A work that lives in two top collections shares its `§` tags between both trees, on purpose; the details panel then shows "also in tree: X" (`State.otherTrees`, `workTreeKeys`). The library tree is unrestricted: renaming there also renames the tag on works of collection trees.
17. **Orphaned heading tags.** If a heading is renamed where the plugin does not run (another computer), the items keep the old `§` tag. `refreshOrphans()` (`organizerState.ts`, after every `reload`/`loadScope`) counts the `§` tags inside the tree's scope (`buildCountMap(libraryID, scope)`) and diffs them against the tree (`orphanHeadingTags`, `src/features/organizer/logic/outline.ts`). The tree column shows a button with the count; the overlay (`organizerOrphans.ts`) lists tags only and assigns each to a heading through the scoped `renameTag`, or removes it through the scoped `purgeTag`.

18. **The citation dialog reads `io` once, from `window.arguments`; a reload loses the arguments.** Verified in the test suite (persistent window, `location.reload()`): afterwards `window.arguments` is `undefined`, `onLoad` throws at `window.arguments[0]`, and `DIALOG_STATE.loaded` never becomes true. Reusing the window with a stable io proxy plus reload is therefore not possible. Each request opens a new window at the old rect (position and size as `openWindow` features, in device pixels; the size is also written to `windowParams`). Windows' docking (snap) belongs to the OS window and is not kept by a new window. `onLoad` reads `io = window.arguments[0].wrappedJSObject` once (`integration/citationDialog.js:60-62`), and the handlers `Helpers`, `SearchHandler`, `PopupsHandler` and `KeyboardHandler` take that `io` in their constructors (`:78-81`). A reload does not change `window.arguments`, and assigning a new `window.io` does not rebind the handlers. Reusing an open dialog for a second request is therefore not possible. Probable cause of the earlier persistent-window failure (inserts missing after the first citation): accept hit a finished command through the stale `io`. This is derived from the source and was not reproduced on the old branch.
19. **`accept()` removes the item trees and collapses the window.** `cleanupBeforeDialogClosing()` runs first (`citationDialog.js:159`), saves the window size to `integration.citationDialog.windowParams` (`:212`, read via `citationDialog/helpers.mjs:440-442`), and unregisters `collectionsView` and `itemsView` (`:221-222`). Then `accept()` hides the layouts, sets `documentElement.style.minHeight` and calls `resizeTo` in a `setTimeout` (`:161-170`). Un-hiding the old layout shows dead trees, so the persistent window never reuses the accepted dialog; it opens a new browse window instead. Timers: the dialog's own `resizeTo` runs on its window's timer queue. A `setTimeout` from the main window ran before it in our tests, so restores use `win.setTimeout`.
20. **Zotero enforces the window size of the citation dialog.** `LibraryLayout.MIN_WIDTH` is 1000 and is a minimum (`citationDialog.js:510`, `:603-640`, `targetWidth = Math.max(…)` at `:613`). `ListLayout.MIN_WIDTH` is 800 and is a maximum (`:1079`, `targetWidth = Math.min(…)` at `:1180`), so the plugin does not change it. It also sets `documentElement.style.minHeight` (`:624`, `:634`) from the bubble, list, preview and bottom heights plus 400 px (`:607-611`), and grows the window to that when it is smaller (`:615`), which gave 583 px in this layout. `zotero-platform/win/zotero.css` adds `min-width` 800 and 1000 px to `#citation-dialog` (`#citation-dialog[dialog-layout=library]`). Narrowing needs both halves: the CSS `min-width` (our injected style sets it to 0 on `#citation-dialog`) and `MIN_WIDTH` in JS, because `resizeWindow()` still grows the window to `MIN_WIDTH`. The minimum height cannot be lowered without replacing `resizeWindow()`. A load-time resize (`onLoad` → `libraryLayout.init()` → `refreshItemsList`) runs before any injector, so the first resize after opening can still widen the window; tests wait about 2.5 s before resizing.
21. **`addEditCitation` does not await the dialog.** It calls `Zotero.Integration.displayDialog(…)` without `await` (`integration.js:1611`) and then awaits `io.promise` (`:1615`), which resolves on `io.accept` or `io.cancel` (`:1834-1846`). Native `displayDialog` resolves only on `unload` (`:497-512`) and calls `progressBar.show()` after that (`:513`), which is why the orphan progress guard is needed. Consequence for persistent windows: the window may outlive the command, and a `displayDialog` wrapper may resolve on accept without affecting the insertion.
22. **`about:blank` unloads before the dialog loads.** A window opened with a URL first unloads its `about:blank` document. The native code skips it (`integration.js:498`); so must any `unload` listener on the window. DOM timers (`setInterval`/`setTimeout`) registered on `win` while it is still `about:blank` are cancelled upon navigating to the chrome URL; interval loops (e.g. `pinRect`) must be scheduled on the host window (`mainWin()`).
23. **Window coordinates differ.** `screenX`/`screenY` report CSS pixels, but the `left`/`top` features of `openWindow` are read as device pixels: on this 125 % machine a window at `screenX` 700 opened with `left=700` appeared at 560. The persistent window therefore multiplies by `devicePixelRatio`. Measured on Windows only.
24. **The Word error box "Ein Fehler ist beim Update Ihres Dokuments aufgetreten" is `integration.error.generic`** (`chrome/locale/de/zotero/zotero.properties:863`). `execCommand` shows it for any exception that is not an `Alert` and not already displayed (`integration.js:386-420`, `:641-644`); the cause is only in the exception, so check Zotero's debug output (Help → Debug Output) for the stack. The persistent path logs its own errors (`accept` wrapper, `openPersistent`) with `ztoolkit.log` and `Zotero.logError`; if opening fails before the window exists it falls back to the native `displayDialog`.
    The first-attempt failure when citing in an existing document was traced to a Zotero core bug in `Session.prototype.resetRequest` (`integration.js:1914`): `getSession` sets `session.rebuildCiteprocState = true` (`:574`), but `resetRequest` unconditionally cleared the flag to `false` before `updateFromDocument` ran, skipping `this.restoreProcessorState()` (`:1192-1195`) and leaving citeproc's `citationById` registry empty. This caused `TypeError: can't access property "citationItems", c is undefined` during cluster preview and a follow-up failure on accept. Patched in `citeOnly/integrationPatch.ts` to preserve `rebuildCiteprocState` across `resetRequest`.
25. **Native `Session.prototype.cite` creates an empty footnote before opening the dialog.** When `addEditCitation` or `addAnnotation` is called from Word/Writer without an existing field at the cursor, `Session.prototype.cite` (`integration.js:1536`) calls `await this.addField(true)` before displaying the dialog. If the persistent dialog is active, this placeholder footnote would be left in the document if the user cancels or closes the dialog. FlexAnnotate patches `Zotero.Integration.Interface.prototype.addEditCitation` and `addAnnotation`: when persistent mode is active and the command is not editing an existing field (`cursorInField`) and has no pending insert, it checks `canInsertField()`, stores `lastCommand`, sets `session._dontActivateDocument = true` (to keep focus on Zotero instead of Word returning to the document, `integration.js:326`), schedules `openBrowse()`, and returns `[]` immediately without running `session.cite()`. The actual footnote is only inserted when the user accepts an item from the browse window (via `insertFromBrowse()`).

## Teardown

`onShutdown` calls `stopAll(features)` in reverse order: patches are restored through `assignChecked` (`_insertCitingResult`, `translate`, per-window `Zotero_File_Interface` methods, `Reader.open`), the citation dialog watcher detaches all injectors (including those in open dialogs), `MenuManager` menus are unregistered by key, the annotation index unloads its notifier observer, `OrganizerFactory.closeWindow()` closes any open Organizer window, and `ztoolkit.unregisterAll()` removes toolkit UI. `removeFromWindow` removes the toolbar button, item-menu entries and the annotation popup of each window. Each patch checks its target before patching and verifies the result after; on failure only that feature disables itself and logs a warning.
